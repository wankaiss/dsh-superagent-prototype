## B1. Scope and boundaries

Build the console in panel/.

The supplied scaffold is Vite 8, React 19, strict TypeScript, Tailwind 4, shadcn/ui on Base UI, TanStack Query and TanStack Router, with a proxy and Origin guard in vite.config.ts. Inspect the actual scaffold and installed APIs before implementing; report material differences.

You may read host files to understand the contract. Change nothing outside panel/. Preserve the proxy, Origin guard and loopback restrictions.

Use installed dependencies first. Add no dependency beyond those installed unless you state why it is necessary. A dependency change does not permit modifying a root lockfile or another file outside panel/; report that constraint if it blocks the change.

Use shared API, route, query-key, token and copy definitions across implementation agents so screens do not independently redefine the same behaviour.

## B2. Contract and caller

Import host API types only with import type from ../../src/app/api.ts, at a panel/src/ boundary where that exact relative path resolves correctly. Deeper modules consume the local adapter/types.

The only permitted host value imports are TICKET_FILTERS and THREAD_FILTERS from that API module. Never import another host runtime module.

Implement a typed call(route, request) modelled on src/client/api.ts:
- Use only methods, routes, request shapes and response types present in the contract.
- Send x-orchestrator-request: 1 on every management API request.
- Preserve the host's message, code and validation details as appropriate.
- Classify failures as offline for a rejected fetch, restarting for the documented empty-body 404, setup for the documented setup envelope, user error for code, validation for issues, or status error.
- Follow the existing caller's discrimination and precedence where shapes overlap.
- Treat intentional cancellation separately from offline failure.
- Handle malformed or unexpected bodies explicitly; never convert them to a successful empty response.
- Distinguish an ordinary missing resource from the specific restarting response.

Resolve discrepancies between the digest and source contract in the report. Do not invent compatibility routes, weaken types or manufacture successful data to hide a mismatch.

## B3. Data, polling and freshness

Use TanStack Query hooks per route with query keys covering the route, record identity and all request/filter parameters.

Preserve these polling intervals:
- State and overview: 3 seconds.
- Lists: 5 seconds.
- A working Ticket's detail: 2 seconds.

Determine working status from the response and re-evaluate its interval as status changes. Use documented or existing behaviour for other reads and report any unresolved freshness policy.

Start no interval polling while the tab is hidden; refetch active data on focus. Avoid duplicate polling timers outside the shared query layer.

For a background refresh failure:
- Retain the last successful data for that same query identity.
- Show a scoped stale marker, last successful fetch time and the current error.
- Distinguish the fetch time from the record's own last-activity timestamp.
- Clear the failure marker after a successful refresh.

Do not show another Ticket, Thread, filter or search query's cached result as the current selection. Do not replace existing content with a skeleton during an ordinary background refresh.

The user-facing stale marker represents a refresh/freshness problem, not TanStack Query's isStale flag by itself. Loading, initial failure, successful empty response and stale retained data are separate UI states.

No fixtures or SAMPLE data anywhere in src/. Do not import them from elsewhere into the production bundle, use them as API fallbacks, or seed the live service to make a screen look populated.

## B4. Routes and navigation

Use a code-based TanStack Router tree with exactly these product routes:
- /
- /tickets, with search parameter state
- /tickets/$id
- /threads, with search parameter filter
- /threads/$key
- /decisions, with search parameter kind
- /sources
- /system

Validate search parameters against supported values and preserve filters through navigation and browser history. Use the contract's filter keys rather than sending display labels as request values. Handle IDs and Thread keys through the router's parameter encoding.

⌘K/Ctrl+K opens search from anywhere, with a visible trigger and accessible modal behaviour. It is an overlay, not a new product route.

Implement search only through existing documented API capabilities. If the contract cannot support the requested scope, report the gap; do not invent an endpoint or claim that searching a partial cache covers all records.

Use contract-backed destinations for Thread, PR and DSH links. Do not guess hostnames, ports or Session URL templates.

## B5. Permitted writes

Only these management writes are allowed:
- Executor pause/resume through POST executor/pause.
- Ticket stop.
- Ticket retry.
- Trigger requeue.
- Decision dismiss.
- Thread unsubscribe.

The management API prefix remains /orchestrator/api/*. Obtain the exact methods, route keys, payloads, eligibility and effects for each operation from the contract. The operation names above do not authorise invented endpoint paths.

Every write follows:
confirmation stating target and documented effect → pending state → toast with the host-confirmed result or error → invalidate affected queries.

Apply these rules consistently:
- The Executor switch opens confirmation before sending; cancelling preserves its current state.
- Explain documented consequences, without claiming that pause stops existing Workers or that Stop reverses previous effects unless the contract says so.
- Prevent duplicate submissions and automatic mutation retries.
- Base eligibility on documented rules and usable current data. Explain disabled actions when eligibility cannot be established.
- Show pending state without prematurely changing stages, totals or pause status.
- Do not equate request acceptance with completed work.
- Preserve actionable errors in context as well as in the toast.
- After a lost response, say the outcome is unconfirmed; do not claim nothing changed. Refetch relevant existing GETs, but claim success only when their evidence actually establishes the result of the action.
- Dismissing a dialog does not imply cancellation of an already-sent request.

Keep settings and prompt editing out of this console. Theme switching is presentation behaviour and does not call a settings API.
